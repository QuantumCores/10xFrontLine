# Frame Brief: Playwright access to valid login codes

> Framing step before /10x-plan. This document captures what is *actually*
> at issue, separated from what was initially assumed.

## Reported Observation

The code generated by the API is not available to the separate step-by-step
Playwright CLI run when exercising the positive login scenario.

## Initial Framing (preserved)

- **User's stated cause or approach**: Playwright needs access to some externally available representation of the generated code.
- **User's proposed direction**: Either accept one fixed development-only code or store each generated code somewhere such as a file.
- **Pre-dispatch narrowing**: The scenario only needs to prove that the application accepts a valid OTP; it does not need to prove real email delivery.

## Dimension Map

The observation could originate at any of these dimensions:

1. **Developer visibility** — Development already logs the generated code, but this is manual and unstructured.
2. **Process boundary** — the plaintext code is captured inside the API process and is unavailable to a separately running Playwright process. ← initial framing
3. **Code generation** — the generator is cryptographically random and has no injected E2E implementation.
4. **Verification** — a universal accepted code would bypass the normal relationship between issuance and verification.

## Hypothesis Investigation

| Hypothesis | Evidence | Verdict |
| --- | --- | --- |
| The code is not available anywhere | Development logs the raw email and code in `PasswordlessAuthService.cs:52-55`. | NONE |
| A separate Playwright process lacks a structured access seam | `CapturedEmailStore` is process-local, and no route exposes it. | STRONG |
| Existing tests require deterministic generation | API tests retrieve the real generated code from `CapturedEmailStore` and successfully verify it. | NONE |
| A universal verifier code is required | Normal generation can remain active if the issued code crosses the test boundary. | NONE |
| Deterministic generation is a viable alternative | Generation is currently a private static method, while the app already has an exact `Testing` environment and DI conventions. | WEAK |

## Narrowing Signals

- The browser scenario needs the request-code and verify-code UI path to remain real.
- Email-provider delivery is outside the scenario boundary.
- The existing API tests already demonstrate that captured delivery can supply the real code without weakening validation.
- A standalone CLI cannot resolve services from the API's dependency-injection container.

## Cross-System Convention

Authentication tests normally replace or capture the delivery adapter, then
retrieve the credential from that test double. This keeps issuance, expiry,
identity binding, hashing, consumption, and rejection behavior intact while
excluding the external email provider.

For an in-process test host, direct access to the capture store has the smallest
surface. Across a process boundary, a narrowly scoped test transport is needed.
A file or application log is an incidental transport and creates stale-read,
parallel-run, cleanup, and credential-retention risks.

## Reframed Problem Statement

> **The actual problem to plan around is**: the API has an established captured-email test seam, but it has no safe, deterministic transport across the process boundary to the standalone Playwright run.

Authentication behavior is not broken, and Playwright does not need a master
code. The missing capability is test-only access to the real issued code, with
isolation strong enough that the capability cannot be enabled accidentally in
Development, Staging, or Production.

## Confidence

- **HIGH** — the existing integration tests prove captured-code retrieval, the standalone process boundary explains the gap, and an independent security pressure test reached the same conclusion.

## What Changes for /10x-plan

The plan should provide a browser-test access seam around captured delivery and
strictly isolate it to an exact E2E environment. It should preserve normal OTP
generation and verification and explicitly prevent a universal verifier bypass
or broadly enabled raw-code endpoint.
